# Refactoring Plan: ClickFlash Ecosystem "Singularity" Audit

This document outlines the actionable steps to execute a "Gold Master" refactoring of the ClickFlash ecosystem, strictly adhering to offline-first principles, deterministic state management, and optimized resource utilization.

## 1. Architectural Bottlenecks (Summary)

1.  **Sync Conflict Resolution (LWW vs CRDT):** `SyncManager.ts` relies on vulnerable Last-Write-Wins (LWW) based on wall-clock timestamps. It lacks vector clocks/CRDTs, making it susceptible to clock drift and data loss during concurrent offline edits.
2.  **Sync Queue Head-of-Line Blocking:** `cloudSyncService.ts` implements strict linear replay (`ORDER BY sequence_number ASC`) but breaks the loop on the first error. This head-of-line blocking stalls the entire synchronization pipeline if a single payload fails.
3.  **Hydration Loops & Batch Stalling:** The boot queue hydration blindly resets failed operations older than 1 hour back to 'pending'. A permanently failing operation will perpetually stall the `LIMIT 50` batch processing due to the strict sequentiality requirement.

## 2. Execution Plan

### Step 1: Data Synchronization Layer (SyncManager & CloudSync)

**Objective:** Implement robust CRDT-style conflict resolution and eliminate queue blocking.

*   **File:** `apps/master/backend/services/SyncManager.ts`
    *   **Action:** Refactor `resolveConflict` to implement Vector Clocks instead of LWW. Introduce a `.vector_clock` JSON column/field parsing for `SyncEntity`.
*   **File:** `apps/master/backend/services/cloudSyncService.ts`
    *   **Action:** Refactor `applyRemoteOperations` and queue processing. Implement a Dead Letter Queue (DLQ) pattern. If an operation fails `MAX_RETRIES` times, move it to a DLQ state rather than halting the entire queue or perpetually retrying every hour.
    *   **Action:** Add jitter to the exponential backoff in `scheduleNextSync` to prevent thundering herd restarts.

### Step 2: Security & IPC Bridge Layer

**Objective:** Enforce context isolation and patch timing vulnerabilities.

*   **File:** `apps/master/preload.js`
    *   **Action:** Fix memory leak in `ipcRenderer.on`. Return a cleanup function (`() => ipcRenderer.removeListener(channel, handler)`).
    *   **Action:** Audit `INVOKE_CHANNELS`. Remove unused `updater:*` channels if they are unhandled in the main process, or stub the handlers to prevent silent failures.
*   **File:** `apps/master/electron-main.js`
    *   **Action:** Patch the timing attack vulnerability in `ipcMain.handle("kiosk:unlock", ...)`. Replace direct string comparison (`pin !== expected`) with `crypto.timingSafeEqual`.

### Step 3: Performance & Memory Optimization

**Objective:** Optimize large dataset handling and DB maintenance.

*   **File:** `apps/master/backend/routes/collections.ts`
    *   **Action:** Refactor the `/collections/photos` endpoint. Replace the load-all query with cursor-based or limit/offset pagination to prevent memory pressure when loading 1000+ photo albums into RAM.
*   **File:** `apps/master/backend/services/maintenanceService.ts` (or equivalent schedule)
    *   **Action:** Ensure `ANALYZE` is executed immediately following the weekly `VACUUM` to rebuild SQLite query planner statistics.

### Step 4: Edge Cases & Failure Recovery

**Objective:** Ensure graceful shutdown and ACID compliance.

*   **File:** `apps/master/backend/server.ts`
    *   **Action:** Refactor the `gracefulShutdown` logic. Implement `Promise.allSettled` to wait for all services (`tunnelManager`, `cloudSyncService`, `queueProcessor`) to stop. Exit with code `1` if any fail, preventing silent corruption. Ensure database connections are explicitly closed inside a transaction boundary if applicable.
*   **File:** `apps/master/backend/services/OrderValidationService.ts` (if exists, or related order logic)
    *   **Action:** Fix non-idempotent check-then-act race conditions in order claiming/validation by using atomic `UPDATE ... WHERE status = 'pending'` queries.

### Step 5: UI State Management (Optimistic Updates)

**Objective:** Ensure deterministic UI state.

*   **File:** `apps/master/src/services/api/photoService.ts` (or equivalent frontend stores)
    *   **Action:** Audit batch operations (e.g., `batchSavePhotos`). Implement explicit rollback mechanisms (snapshotting state before mutation) for optimistic UI updates to recover cleanly if the IPC/DB write fails.
