# Touch App Photo Flow Audit

> **Scope:** ClickFlash Touch Kiosk (photographer-side kiosk)  
> **Version:** 4.2.0  
> **Date:** 2026-06-12  
> **Auditor:** Hermes Agent

## 1. Touch Photo Capture Paths (Every Entry Point)

### 1.1 Primary Path: Master → Touch Folder Drop ("Titan Protocol")
The **dominant** photo ingress is **not** tethered capture inside Touch. Instead, the **Master station** (port 8090) exports finalized albums into Touch's monitored `uploads/` directory, and Touch's backend watches for them.

- **File:** `apps/touch/backend/services/watcherService.ts` (lines 83–170)
- **Mechanism:** `chokidar` watches `UPLOAD_DIR` (default `pb_data/uploads`) with these settings:
  ```ts
  chokidar.watch(this.uploadDir, {
    ignored: [/(^|[\/\\])\../, /\.processed$/, "**/temp/**"],
    persistent: true,
    ignoreInitial: false,
    depth: 1,
    awaitWriteFinish: { stabilityThreshold: 2000, pollInterval: 100 },
  });
  ```
- **Trigger:** When an `album-*` folder appears containing `metadata.json`, `WatcherService.triggerImport()` runs (line 117).
- **What it imports:**
  - Reads `metadata.json` for album metadata (title, date, roomNumber, photographerId, categories, photos array).
  - Iterates `metadata.photos` and inserts into SQLite `photos` table with `INSERT OR IGNORE` (line 147).
  - Runs face indexing on each imported photo via `faceService.analyzeImage()` (line 163).
  - Broadcasts a realtime SSE event (`action: "create"`, `collection: "albums"`) (line 195).

### 1.2 Secondary Path: HTTP Pull from Master (SyncService)
Touch's frontend `SyncService` actively **pulls** photos from Master when the kiosk is online.

- **File:** `apps/touch/src/services/syncService.ts` (lines 471–805)
- **Endpoint hit:** `GET {masterUrl}/api/collections/albums/records?filter=(status='Finalized')&expand=photos_via_album` (line 483)
- **Photo download:** For each photo in the album, Touch calls its **own backend** `POST /api/sync/pull-photo` (line 756), which then downloads the JPEG from Master via `http.get()` and saves it locally (line 64 in `sync.ts`).
- **Concurrency:** `MAX_CONCURRENT_DOWNLOADS = 3` (line 77 in `syncService.ts`).
- **Batch size:** `BATCH_SIZE = 5` albums at a time (line 78).

### 1.3 Tertiary Path: Manual / Hot-Folder Upload via Collections API
Touch exposes a PocketBase-compatible collections API that can accept `multipart/form-data` uploads.

- **File:** `apps/touch/backend/routes/collections.ts` (lines 500–650)
- **Route:** `POST /api/collections/:collection/records` (formidable-based)
- **Behavior:** If `table === "photos"`, the backend writes the uploaded file to `UPLOAD_DIR` and inserts a DB record. There is a **read-only guard** for albums/photos from non-localhost IPs (lines 154–214), but localhost uploads are allowed.
- **Hot-folder note:** The code references `importDir` (from settings key `photoImportDir`) for copying files into the uploads tree (lines 537–608), but the actual tether/Lightroom plugin logic lives in the **Master** app, not Touch.

### 1.4 No Native Tethered Capture in Touch
**There is NO direct tethered shooting, Lightroom plugin, or SD-card import logic inside the Touch app.** Touch is a **consumer** of photos, not a producer. The photographer tethers/captures on the Master workstation (or a separate machine), and Master pushes albums to Touch via:
1. Folder drop (watcher)
2. HTTP pull (sync)
3. WebSocket real-time notification (see §3)

| `AUDIT_LOGS_DIR` | `DATA_DIR/audit_logs` | Audit trail |
| `ORDERS_DIR` | `DATA_DIR/orders` | Exported order files |

### 2.2 Photo File Organization
Handled by `PhotoProcessor` (`apps/touch/backend/shared/photoProcessor.ts`):

- **Album-scoped directories:** `uploads/{albumId}/`
- **Original filename preserved:** `photoId{ext}` (e.g., `photo-abc123.jpg`)
- **Relative path stored in DB:** `{albumId}/{photoId}{ext}` (line 118)
- **Kiosk version generated:** `kiosk_{photoId}{ext}` (line 27 in `photoWorker.ts`)
  - Resized to **2048×2048 fit-inside** (line 31)
  - JPEG quality **80** (line 32)

### 2.3 Thumbnail / Preview Strategy

| Tier | Size | Quality | Generated By | Stored At |
|------|------|---------|--------------|-----------|
| Original | Native | 100% | Master upload | `uploads/{albumId}/{photoId}.jpg` |
| Kiosk | 2048×2048 max | JPEG 80 | `photoWorker.ts` (Worker Thread) | `uploads/{albumId}/kiosk_{photoId}.jpg` |
| Thumbnail | Not explicitly generated in Touch | — | — | `thumbnailUrl` column exists but unused in current code |
| Tiny/Preview | Not generated | — | — | `tinyUrl`, `previewUrl` columns exist (migration 014) but no worker generates them |

**Note:** The `photoWorker.ts` only creates a single kiosk JPEG. There is **no WebP conversion**, no multi-resolution pyramid, and no on-the-fly thumbnail generation endpoint.

- **Indexes:** `idx_photos_fileHash`, `idx_photos_albumId`, `idx_photos_roomNumber`, `idx_photos_sync_id`.

### 2.5 IndexedDB (Browser-side Cache)

- **File:** `apps/touch/src/services/db.ts`
- **Tables:** `albums`, `orders`, `offlineQueue`, `analyticsEvents`, `analyticsSessions`, `checkpoints`, `conflicts`
- **Photos are NOT stored in IndexedDB.** Only album metadata and order mutations are cached client-side. Photos are served via HTTP from the backend `files.ts` route.

## 3. Touch → Master Transfer Protocol

### 3.1 Direction Clarification
Touch **does not push photos to Master.** Photos flow **Master → Touch** (pull or folder drop). Touch **pushes orders** to Master.

### 3.2 Order Push Protocol (for completeness)
- **File:** `apps/touch/src/services/syncService.ts` (lines 386–469)
- **Endpoint:** `POST {masterUrl}/api/orders/kiosk/orders`
- **Body:** JSON with `clientMutationId`, `clientDeviceId`, `items`, `clientName`, `email`, `total`, `status`, `date`, `destinationId`, `photographerId`, `roomNumber`, `appliedDiscount`
- **Timeout:** `AbortSignal.timeout(15000)` (line 438)
- **Idempotency:** `clientMutationId` prevents duplicate orders on retry (line 418)
- **Deduplication response:** Master may return `208 Already Reported` (line 441)

### 3.3 Photo Pull Protocol (Master → Touch)
- **Frontend initiates:** `SyncService.downloadAndSavePhoto()` calls `POST {baseUrl}/api/sync/pull-photo` (line 756 in `syncService.ts`)
- **Backend handler:** `apps/touch/backend/routes/sync.ts` (lines 49–178)
- **Request shape:**
  ```json
  {
    "url": "http://master:8090/api/files/photos/...",
    "filename": "photo.jpg",
    "photoId": "...",
    "albumId": "...",
    "photographerId": 0,
    "title": "..."
  }
  ```
- **Download mechanism:** Node.js `http.get()` with `streamPipeline` (line 64), 120s timeout.
- **Processing:** `photoProcessor.processPhoto()` generates kiosk JPEG via Worker Thread, moves file to `uploads/{albumId}/`, inserts/updates SQLite record.
- **Transaction:** `dbManager.transaction()` with `INSERT OR UPDATE` logic (lines 110–140).
- **Retry:** `MAX_RETRY_ATTEMPTS = 3` with exponential backoff (`RETRY_BACKOFF_BASE = 1000ms`) (lines 74–76 in `syncService.ts`).

### 3.4 WebSocket Real-Time (Master → Touch)
- **File:** `apps/touch/src/services/webSocketService.ts`
- **URL:** `ws://{masterIp}:3001` (line 84)
- **Messages received:** `NEW_ALBUM_FOR_KIOSK`, `ALBUM_UPDATED`, `PHOTO_UPDATED`, `ORDER_UPDATED`, `USER_UPDATED`, `NEW_ORDER_NOTIFICATION` (line 217)
- **On receive:** Triggers `onRefreshCallback()` which typically re-fetches albums.
- **Reconnection:** Exponential backoff up to 30s, max 100 attempts (lines 163–178).
- **Heartbeat:** 30s PING/PONG (lines 189–196).

### 3.5 mDNS Discovery (Touch finds Master)
- **File:** `apps/touch/backend/services/mdnsDiscovery.ts`
- **Library:** `bonjour-service`
- **Touch advertises:** `clickflash-touch` on port 8091 (line 27)
- **Touch browses for:** `clickflash` type (line 42)
- **Latency ranking:** Pings `http://{address}:{port}/api/health` and sorts by latency (lines 54–59)
- **Pairing:** QR scan or mDNS discovery → `POST /api/pairing/complete` → HMAC secret exchange (file: `backend/routes/pairing.ts`)

## 4. Touch Kiosk Display

### 4.1 Photo Loading in UI
- **File:** `apps/touch/src/components/touch/PhotoSelectionScreen.tsx` (lines 20–47)
- **Component:** `PhotoCard` renders `<img src={photo.url} loading="lazy" />`
- **URL resolution:** `photoService.ts` (lines 35–38) prepends `pb.baseUrlValue` to relative URLs:
  ```ts
  photoUrl = `${baseUrl}/api/files/photos/${p.id}/${p.url}`;
  ```
- **Virtual scrolling:** `VirtualGrid` is used when album photo count exceeds `VIRTUAL_SCROLL_THRESHOLD = 50` (line 14).

### 4.2 Full-Res Preview
- **File:** `apps/touch/src/components/touch/PhotoPreviewScreen.tsx` (line 162)
- **Display URL:** `photo.url` directly (no separate preview tier).
- **Zoom:** Client-side zoom up to 4× with pan (lines 45–130).
- **Watermark:** Optional overlay from `localStorage` watermark settings (lines 164–184).

### 4.3 Caching / Prefetch
- **Backend file serving:** `files.ts` (lines 95–119) sets:
  - `Cache-Control: public, max-age=86400`
  - `ETag` based on file path + mtime + size
  - `Accept-Ranges: bytes` (supports range requests)
- **No explicit prefetch** in the frontend. Photos are fetched on-demand when the album grid renders.
- **No service worker** or offline image cache detected in the current codebase.

### 4.4 Format Support
- **Served formats:** JPEG, PNG, GIF, WebP (MIME mapping in `files.ts`, lines 86–92)
- **No on-the-fly WebP conversion** or responsive `<picture>` element usage.

## 5. Touch Offline Behavior

### 5.1 Offline Queue (Orders)
- **File:** `apps/touch/src/services/OfflineQueueV2.ts`
- **Storage:** IndexedDB (`StarTouchDB` table `offlineQueue`)
- **Max queue size:** `kioskConfig.offline.maxQueueSize = 100` (from `kioskConfig.ts`, line 35)
- **Max retries:** `MAX_RETRIES = 5` (line 42)
- **Retry backoff:** `RETRY_BACKOFF_BASE = 1000ms` (line 43)
- **Dead letter queue:** Items exceeding max retries become `status: 'dead'` (line 232)
- **Trigger:** `window.addEventListener('online', ...)` and custom `socket-connected` event (lines 62–71)

### 5.2 Photo Sync Offline Behavior
- **SyncService** (`syncService.ts`) checks `navigator.onLine` implicitly via `fetch` failures.
- **Failed photo downloads** are persisted to `localStorage` key `syncServiceFailedPhotos` (line 126 in `syncService.ts`).
- **Retry logic:** `retryFailedPhotos()` runs during every sync cycle (lines 295–297, 317–380).
- **Max retry attempts:** `MAX_RETRY_ATTEMPTS = 3` (line 74).
- **After max retries:** Photo is removed from queue and logged as permanent failure (line 324).

### 5.3 Connectivity Service
- **File:** `apps/touch/src/services/connectivityService.ts`
- **Probe interval:** 10s when offline (line 28)
- **Probe timeout:** 5s (line 29)
- **Debounce:** 2s to prevent flapping (line 31)
- **Endpoint:** `HEAD {masterUrl}/api/health` (line 102)

### 5.4 IndexedDB Album Cache
- `offlineStorage.saveAlbums()` stores album metadata in IndexedDB (`db.ts`, version 5 schema).
- Photos themselves are **not cached** in IndexedDB; if offline, images already loaded by the browser may be in the HTTP cache, but new albums/photos are unavailable.

## 6. Photo Idempotency Map

### 6.1 Deduplication Strategy

| Layer | Key | Method | File |
|-------|-----|--------|------|
| **File hash** | `fileHash` (SHA-256) | `photoProcessor.findDuplicateByHash()` | `backend/shared/photoProcessor.ts` line 188 |
| **Database** | `id` (UUID) | `INSERT OR IGNORE INTO photos (id, ...)` | `backend/services/watcherService.ts` line 147 |
| **Database** | `id` | `INSERT OR REPLACE` / `UPDATE` in `sync.ts` | `backend/routes/sync.ts` lines 110–140 |
| **Sync checkpoint** | `photoId` | `syncCheckpointService.isPhotoProcessed()` | `src/services/syncCheckpointService.ts` line 238 |
| **Session memory** | `photoId` | `processedPhotoIds` Set (cleared hourly) | `src/services/syncService.ts` lines 80, 119 |

### 6.2 Hash Calculation
- **Worker thread:** `photoWorker.ts` line 12 calculates SHA-256 via `crypto.createHash('sha256')` streaming over the file.
- **Used for:** Duplicate detection when importing via folder watcher or HTTP pull.
- **Not used for:** SyncService photo pull (relies on `photoId` UUID from Master).

### 6.3 Order Idempotency
- `clientMutationId` = `kiosk-${order.id}-${order.created || Date.now()}` (line 418 in `syncService.ts`)
- Master returns `208` if already seen (line 441).

## 7. Photo Failure Recovery

### 7.1 Sync Failure Modes

| Failure | Behavior | Retry | User Notification |
|---------|----------|-------|-----------------|
| Master unreachable (heartbeat fails) | Sync skipped, state set to `lastSyncError: 'Master unavailable'` | Backoff loop (15s → 5min) | `SyncStatusIndicator` + `WelcomeScreen` offline banner |
| Photo download fails | Added to `failedPhotoQueue` in `localStorage` | Up to 3 retries with exponential backoff | None (silent, logged) |
| Photo download max retries exceeded | Removed from queue, permanently lost for this session | None | None |
| Network error mid-sync | `consecutiveSyncFailures++`, interval doubles | Next sync cycle | Logged only |
| Backend `/api/sync/pull-photo` fails | `downloadAndSavePhoto` returns `false`, retry queued | Via `retryFailedPhotos()` | None |

### 7.2 Watcher Failure
- `WatcherService` errors are caught and logged (line 97 in `watcherService.ts`).
- Face indexing failures are **non-fatal**; the photo is still imported (line 176).
- No automatic restart of the watcher if it crashes; only stopped on graceful shutdown (`server.ts` line 572).

### 7.3 Checkpoint Resume
- `syncCheckpointService` saves progress to IndexedDB every batch (lines 552–563 in `syncService.ts`).
- On resume, already-processed albums/photos are skipped (lines 500–510, 593–596, 648–656).
- Checkpoint expires after **24 hours** (`CHECKPOINT_EXPIRY_MS`, line 44 in `syncCheckpointService.ts`).

## 8. Gaps & Risks

### 8.1 Critical Gaps

| # | Gap | Risk | Evidence |
|---|-----|------|----------|
| 1 | **No native tether / Lightroom / hot-folder in Touch** | Touch cannot receive photos unless Master is operational and network is up. | No tether/Lightroom code found in `apps/touch`. Watcher only watches `album-*` folders. |
| 2 | **Only one kiosk JPEG tier generated** | No true thumbnail/preview pyramid. Large galleries may load 2048px images for grid view, wasting bandwidth. | `photoWorker.ts` only resizes to 2048. `tinyUrl`/`previewUrl` columns exist but are never populated. |
| 3 | **No WebP conversion** | JPEG-only pipeline misses modern compression gains. | `photoWorker.ts` hardcodes `.jpeg({ quality: 80 })`. |
| 4 | **Photos not cached offline** | If Touch goes offline after initial sync, photos already viewed may be in browser HTTP cache, but there is no guaranteed offline gallery. | `offlineStorage.ts` only caches `Album` and `Order` objects, not photo blobs. |
| 5 | **No explicit queue size limit for failed photos** | `failedPhotoQueue` is stored in `localStorage` (unbounded). Could grow large. | `syncService.ts` line 126 uses `localStorage.setItem('syncServiceFailedPhotos', ...)`. |
| 6 | **No user-facing retry UI for photos** | Customers cannot see if photos are missing due to sync failures. | `WelcomeScreen` shows offline banner, but `PhotoSelectionScreen` has no "sync in progress" or "missing photos" indicator. |
| 7 | **Watcher depth = 1** | Nested album folders (>1 level deep) are ignored. | `watcherService.ts` line 86: `depth: 1`. |
| 8 | **Face indexing on watcher import is synchronous-blocking** | `triggerImport` awaits `faceService.analyzeImage()` for every photo in a loop, blocking the queue. | `watcherService.ts` lines 163–176: `for (const photo of metadata.photos) { await faceService.analyzeImage(...) }` |
| 9 | **No checksum verification on downloaded photos** | `sync.ts` checks `stats.size > 0` but does not verify SHA-256 against Master's hash. | `sync.ts` lines 79–83. |
| 10 | **Kiosk JPEG is generated even for pull-sync** | Every pulled photo gets a 2048px JPEG copy, doubling storage. | `photoProcessor.processPhoto()` always runs the worker. |

### 8.2 Security Risks

| # | Risk | Evidence |
|---|------|----------|
| 1 | `files.ts` regex route may expose files outside `UPLOAD_DIR` if path normalization is bypassed | `files.ts` line 22: `router.get(/^\/(.*)/, ...)` with manual path splitting. |
| 2 | `sync.ts` `pull-photo` accepts arbitrary `url` — potential SSRF if auth middleware is skipped | `sync.ts` line 51: `const { url, filename, photoId, albumId } = req.body;` then `http.get(url)`. |

## 9. Open Questions

1. **Where is the Master-side export logic?** The audit only covers Touch. The Master app (`apps/master/`) presumably contains the Lightroom plugin / tether capture / hot-folder watcher that creates the `album-*/metadata.json` bundles. That was out of scope for this audit.
2. **What is the expected photo volume per event?** The `VIRTUAL_SCROLL_THRESHOLD = 50` and `MAX_CONCURRENT_DOWNLOADS = 3` suggest small-to-medium galleries. Has this been tested with 500+ photos?
3. **Why is `failedPhotoQueue` in `localStorage` instead of IndexedDB?** `OfflineQueueV2` uses IndexedDB, but `SyncService` uses `localStorage` for failed photos, risking the 5MB limit.
4. **Is the kiosk JPEG actually used by the frontend?** The frontend `photoService.ts` constructs URLs using `pb.baseUrlValue + /api/files/photos/{id}/{url}`, which serves the **original** file via `files.ts`, not the `kiosk_` version. The kiosk resize may be dead code.
5. **What happens if the watcher and syncService both try to import the same album?** Both use `INSERT OR IGNORE`, but the watcher runs face indexing while syncService does not (directly). Could lead to inconsistent face index state.
6. **Is there a cleanup job for old `pb_data/uploads` files?** No reference to pruning or archive logic found in Touch backend.
7. **Does the Master WebSocket server (port 3001) push actual photo bytes, or just metadata?** The WebSocket service only triggers refresh callbacks; photos are still pulled via HTTP.
