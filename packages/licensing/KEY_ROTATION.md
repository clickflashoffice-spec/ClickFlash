# Ed25519 Key Rotation Standard Operating Procedure

This document outlines the procedure for rotating the Ed25519 licensing keys used within the ClickFlash ecosystem.

## Why Rotate Keys?
Keys should be rotated periodically or immediately upon suspected compromise. A compromised private key allows an attacker to forge valid licenses with arbitrary parameters (e.g. infinite lifetime, enterprise features, arbitrary machine IDs).

## Architecture Context
- **Private Key**: Kept entirely secure. Only used by the secure License Generator tool.
- **Public Key**: Distributed with the Master Portal (`apps/master`), Touch Kiosk (`apps/touch`), and other ecosystem apps that need to validate licenses.

## Key Rotation Procedure

### Phase 1: Generate New Keypair
1. Run the key generator utility to create a new Ed25519 keypair.
   ```bash
   pnpm --filter @clickflash/licensing run generate-keys
   ```
2. Store the **new Private Key** in your secure vault (e.g., 1Password, AWS Secrets Manager) as `CLICKFLASH_LICENSE_PRIVATE_KEY_V2`.
3. Distribute the **new Public Key** to the environment variables (`CLICKFLASH_LICENSE_PUBLIC_KEY`) of all affected applications.

### Phase 2: Dual Key Support (Grace Period)
To prevent immediately invalidating existing active licenses during the rollout:
1. Update the application validation logic to check signatures against **both** the new public key and the legacy public key.
2. Example implementation logic:
   ```typescript
   let result = verifyEd25519License(licenseStr, newPublicKey, options);
   if (!result.valid) {
       result = verifyEd25519License(licenseStr, legacyPublicKey, options);
   }
   ```
3. Deploy the updated apps across the fleet. All clients can now validate licenses generated by either key.

### Phase 3: Issuing New Licenses
1. Update the License Generator tool to exclusively use the new private key for all future licenses.
2. Any newly generated licenses will now be signed with the V2 key.

### Phase 4: Revocation / Legacy Key Deprecation
1. When all V1-signed licenses have naturally expired, or when a forced rollover is required, remove the legacy public key from the application validation logic.
2. If forced rollover is required, use the CRL (Certificate Revocation List) to explicitly ban V1 keys or specific compromised nonces.
3. Deploy the apps. The V1 key is now fully deprecated.

## CRL Support
If a specific license is compromised (but the private key is safe), you can revoke it via the CRL. Add the `nonce` of the compromised license to the `crl` array in the `Ed25519ValidateOptions` when calling `verifyEd25519License`.
